# CycleMap 数学的・アルゴリズム的改善提案

本ドキュメントは、コアルーティングおよびナビゲーションロジックに対して、数学的・物理的・アルゴリズム的な観点から分析した結果に基づく改善提案のリストです。

## 1. 勾配コストモデルの非線形性・非対称性の見直し
* **対象ファイル**: `application/routing-core/src/main/kotlin/com/gorite/cyclemap/routing/Routing.kt` (CyclingCostModel)
* **指摘内容**: 現在の勾配ペナルティ $1.0 + |\text{grade}| \times 0.02$ は絶対値を用いているため、上り坂と下り坂で同等のペナルティが加算されます。しかし、現実の自転車の物理的エネルギー消費（位置エネルギーの獲得と運動エネルギーへの変換）は非対称です。
* **具体的な改善案**: 
  * 上り坂に対しては2次関数的または指数関数的にペナルティを増加させ、下り坂に対してはある一定の勾配まではペナルティをゼロにする、あるいは僅かにマイナスにする非対称なコスト関数（例: トブラーのハイキング関数の自転車向けアレンジ）の導入を検討します。
  * ただし、A*の許容性（Admissibility）を保つため、どのような勾配であっても「距離×最小倍率（0.90）」を下回らないよう数学的な下限クランプを必須とします。

## 2. 勾配ペナルティによる三角不等式の破壊防止
* **対象ファイル**: `application/routing-core/src/main/kotlin/com/gorite/cyclemap/routing/LazyMappedRouting.kt` (gradePenalty)
* **指摘内容**: `FLAT` などの優先方針において、区分的非線形関数（Piecewise non-linear function）を適用して急な上り下りを極端に避ける設定にした場合、グラフ上のエッジコストにおいて三角不等式が成り立ちにくくなります。これにより、ヒューリスティック関数の精度が相対的に低下し、展開ノード数の爆発（探索空間の球状化）を招く恐れがあります。
* **具体的な改善案**:
  * コストペナルティの最大倍率に論理的な上限を設ける。
  * コスト関数やペナルティ係数を変更した際に、ヒューリスティック関数の一貫性（Consistency）と三角不等式が崩れていないかを自動検証するテストケース（ランダムなノード間の最適性チェック）をCIに組み込みます。

## 3. ETA（到着予想時刻）算出アルゴリズムの安定化
* **対象ファイル**: `application/routing-core/src/main/kotlin/com/gorite/cyclemap/routing/NavigationStats.kt` (computeNavigationStats)
* **指摘内容**: ETAの算出において単純な算術平均速度などを過度に信用すると、信号待ちや一時停止などの特異な低速区間によって到着予想時刻が急激に変動（発散）する数学的リスクがあります。
* **具体的な改善案**:
  * 速度の平滑化処理に、指数移動平均（EMA: Exponential Moving Average: $V_t = \alpha v_t + (1-\alpha)V_{t-1}$）や、低周波成分のみを通過させるデジタルローパスフィルタ（あるいはカルマンフィルタの一次元簡略版）を導入し、突発的な停止によるETAのチャタリングを抑制します。

## 4. 地球大圏距離計算の最適化と精度の使い分け
* **対象ファイル**: `application/routing-core/src/main/kotlin/com/gorite/cyclemap/routing/Routing.kt` (haversineMeters)
* **指摘内容**: Haversine公式は真球近似であるため、現実の地球（楕円体）に対して最大約0.3%（10kmで約30m）の幾何学的誤差を含みます。ヒューリスティックとしては十分ですが、ユーザーに提示する最終的な距離表示としては誤差が蓄積する可能性があります。
* **具体的な改善案**:
  * 探索アルゴリズム内部（大量に呼ばれるヒューリスティック関数や第2パスのフィルタリング）では現在のHaversine計算を維持（パフォーマンス優先）。
  * ルート確定後の「総距離」や「残距離」の最終計算パスでのみ、より高精度なVincenty法（またはKarneyのアルゴリズム）を選択的に適用するハイブリッドアプローチを提案します。

## 5. ハッシュインデックスの衝突耐性向上
* **対象ファイル**: `application/routing-core/src/main/kotlin/com/gorite/cyclemap/routing/MappedRouting.kt` (LongIntIndex)
* **指摘内容**: メモリマップを使用しない静的展開時のハッシュテーブルにおいて、線形走査（Linear Probing）を採用していますが、キーの分布によってはクラスタリング（一次集積）が発生し、最悪計算量 $O(N)$ に近づく懸念があります。
* **具体的な改善案**:
  * ロードファクタ（装填率）を厳密に監視し、しきい値を超えた際の動的リサイズを保証するか、線形走査からダブルハッシュ法（Double Hashing）や Cuckoo Hashing などの衝突耐性の高いアルゴリズムへの変更を検討します。

## 6. 双方向探索の終了条件の厳密化
* **対象ファイル**: `application/routing-core/src/main/kotlin/com/gorite/cyclemap/routing/AltRouting.kt` (BidirectionalRouter)
* **指摘内容**: 双方向A*探索（実験機能）において、終了条件（両方向のオープンセットの最小コストの和 $\ge$ これまでに見つかった最短経路コスト）の数学的境界条件は非常にシビアであり、実装のわずかなズレが最適解の取りこぼしにつながります。
* **具体的な改善案**:
  * 意図的に極端な非対称コスト（一方通行が連続する、あるいはペナルティが極端に高い）を持つ小さなモックグラフを作成し、通常のA*と双方向A*の結果が「コスト」と「経路」の双方で完全に一致することを証明する境界値テスト（エッジケース・ユニットテスト）を追加します。
