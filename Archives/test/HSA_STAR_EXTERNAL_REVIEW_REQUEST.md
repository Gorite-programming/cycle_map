# HSA* ルーティングシステム 外部レビュー依頼書

## 1. 目的

Android向け完全オフライン自転車ナビゲーションアプリ CycleMap において、既存A*を基準とした長距離経路探索改善案「HSA*」を検討している。

添付の `HSA* 実装仕様書 v0.3` は、本レビュー依頼書とは別資料としてそのまま添付する。仕様書の設計思想、数値、用語、未確定項目をレビュー対象とする。

外部レビューでは、HSA*の設計妥当性だけでなく、現在の実装方針が本当にA*より有利になるか、改善の優先順位、実装を中止または縮小すべき部分についても意見を求めたい。

## 2. プロジェクト概要

- 対象: Android完全オフライン自転車ナビゲーション
- 対象地域: 山口県
- 実装言語: Kotlin
- 地図表示: GSIタイル
- 道路グラフ: OpenStreetMap由来の独自バイナリグラフ
- Androidグラフ読み込み: mmap + sidecar index
- 現行ルーター: 自作A*
- 目的: 100km以上の長距離経路探索を実機上で安定して実行する
- 優先順位: クラッシュ・OOM・ANRを避けつつ、十分な経路品質と実行時間を確保する

## 3. 現在のグラフ規模

山口県の実グラフで以下の規模を確認している。

- ノード数: 1,688,036
- 有向エッジ数: 3,495,466
- グラフサイズ: 約161.5 MiB
- AndroidではLazyMappedRoadGraphとして読み込む
- 既存の実機検証ではmmap読み込みでOOMを回避できている

## 4. 現在の実装状況

### 4.1 既存A*

- `RoadGraph` + `AStarRouter` がJVM側の基準実装
- Androidでは `LazyMappedRoadGraph.route()` が実際の経路探索を担当
- `CyclingCostModel` を使用
- 道路種別ごとのコスト倍率を持つ
- motorway / motorway_link は除外
- 実際のアプリ経路探索は現在もA*である

### 4.2 HSA* Phase 1

専用ファイル `routing-core/src/main/kotlin/com/gorite/cyclemap/routing/HsaRouting.kt` を追加した。

現在実装しているもの:

- `HsaMode.O / B / F`
- `HsaOptions.fromMode(...)`
- モード値の検証
- 距離に応じたセグメント数計算
- セグメント内のbounded A*
- セグメント接続失敗時の通常A*フォールバック
- JVM `RoadGraph`向けA*/HSA*比較API
- Android `LazyMappedRoadGraph`向け簡易HSA*比較API
- 実行時間、ヒープ増加量、経路距離、セグメント数、フォールバック有無の測定

まだ実装していないもの:

- 道路階層によるArterial Graph
- Skeleton Candidate Generation
- Beam Search
- Candidate Diversity / Overlap管理
- 限定並列実行
- 動的な負荷ベース再分割
- Boundary Repair
- Final Refinement
- ナビ中のPartial Rerouting

したがって、現在のHSA*は仕様書全体の完成版ではなく、直線補間した中間アンカーへ分割してA*を繰り返すPhase 1の実験実装である。

## 5. 実機ベンチマーク結果

Samsung実機上で、山口市から岩国方面の約90km A*経路を基準に測定した。

### A*基準

```text
A* 2.725s / 99.9MB / 90.5km
```

### HSA*-B

```text
HSA*-B 4.659s / 37.5MB / 100.3km
segment=5
fallback=false
```

### 差分

```text
HSA*-O: +2.3s / -71MB / +10km
        90km -> 100km

HSA*-F: +1.3s / -41MB / +23km
        90km -> 113km
```

解釈:

- HSA*はメモリ使用量を削減できている
- しかし現在のHSA*-B/FはA*より遅い
- 経路距離が大きく悪化している
- Fモードは速度を優先する代わりに経路品質がさらに悪化している
- fallback=falseで完了しているため、単純な探索失敗ではなく中間アンカーの選び方が品質低下の主因と考えている

## 6. 現時点の技術的な懸念

### 6.1 中間アンカーの品質

現在のPhase 1では、始点と終点を緯度経度上で直線補間し、それぞれに近いグラフノードを中間アンカーとして選んでいる。

この方法には以下の問題がある。

- 道路ネットワークの実際の接続性を考慮していない
- 山、海、河川、県境、通行不能領域を考慮していない
- 主要道路上のノードを優先していない
- 経路全体のコストを見ずに境界を固定している
- 各セグメントの局所最適解が全体として長い経路になる

### 6.2 HSA*の速度

現状はセグメントごとにA*を繰り返しているだけであり、探索量削減の仕組みが不十分である。

- セグメント数分だけ探索を実行する
- Beam Searchはまだない
- Arterial Graphによる探索空間削減はまだない
- 限定並列化はまだない
- 境界を後から修復していない

このため、HSA*を複雑化する前に、単純なセグメント分割が本当に有効かを再評価する必要がある。

### 6.3 コストとヒューリスティック

以下の統一を実施した。

- `EdgeCostModel` に最小コスト倍率の概念を追加
- `CyclingCostModel` の最小倍率を0.90に設定
- A*のヒューリスティックを距離 × 最小コスト倍率に変更
- HSA*も同じ下限倍率を使用
- Androidのmmapルーターも0.90を使用
- 可変 `costMultiplier` を持つ `DistanceCostModel` は安全側に0.0を使用

ただし、A*とHSA*の品質差が残っているため、コスト単位・道路種別係数・ヒューリスティックの設計が十分に公平か、外部レビューを求めたい。

### 6.4 メモリ計測

現在の実機UIで表示しているメモリ値は、実行中のJVMヒープ増加量である。

- Android全体のPSSではない
- mmap領域やnative memoryを完全には表さない
- GCタイミングの影響を受ける

実機比較の正式指標として、`Debug.MemoryInfo` / `dumpsys meminfo` によるPSSを使うべきか確認したい。

## 7. 外部レビューで確認したい質問

### アルゴリズム妥当性

1. 現在の「直線補間 + 最近傍ノード」方式をHSA*のPhase 1として残す価値はあるか。
2. 中間アンカーを主要道路・道路階層・接続性から選ぶ場合、最小限必要なアルゴリズムは何か。
3. Road Hierarchy、Skeleton Generation、Beam Search、Boundary Repairのうち、最初に実装すべきものはどれか。
4. HSA*という構成は、単純なContraction Hierarchies、ALT、Landmark、HPA*、Multi-Level Dijkstra等と比較して妥当か。
5. 100〜200kmの自転車ルートで、セグメント分割方式が有効になる条件は何か。

### 経路品質

6. HSA*の経路距離がA*より5%以上長い場合にA*へフォールバックする品質ゲートは妥当か。
7. 距離だけでなくCostModelの総コストで品質を判定すべきか。
8. セグメント境界の接続を自然にする実装方法は何か。
9. 中間アンカーを強制せず、候補境界として複数候補を残すべきか。

### Android性能

10. mmapグラフを維持したまま、HSA*の探索状態をどのようにメモリ制限すべきか。
11. Android上での限定並列数は何を基準に決めるべきか。
12. JVMヒープ、PSS、native memory、mmap resident pagesのどれを正式な比較指標にすべきか。
13. A*が約2.7秒で完了する90kmケースに対し、HSA*を導入する価値があるか。

### 実装方針

14. 現段階では実運用をA*に固定し、HSA*を実験機能に限定する判断は妥当か。
15. HSA*の経路品質が改善しない場合、どの段階で開発を中止してA*のメモリ最適化へ戻るべきか。
16. 今後の実装順序として、以下で妥当か。

```text
品質ゲート
  ↓
道路階層付きアンカー候補
  ↓
複数候補保持
  ↓
Boundary Repair
  ↓
Final Refinement
  ↓
Beam Search
  ↓
限定並列
```

## 8. 現時点の暫定判断

- アプリの通常経路探索はA*を継続する
- HSA*は実験・比較用としてのみ使用する
- HSA*を現状のまま本番ナビへ切り替えない
- まず経路品質ゲートと候補アンカー改善を検討する
- メモリ削減だけを目的にHSA*を導入する場合は、経路距離悪化とのトレードオフを明示する
- 100km以上の複数ケースで、時間・PSS・経路距離・Cost Errorを測定する

## 9. 求める回答形式

以下の形式で意見を求めたい。

1. 設計上の重大な問題
2. 現在のベンチマーク結果の解釈
3. HSA*を継続する価値
4. 最優先で修正すべき実装
5. 代替アルゴリズムの提案
6. Android実機での測定方法
7. 仕様書v0.3の修正提案
8. 実装継続・縮小・中止の判断

特に、現在のHSA*が「長距離探索を高速化する設計」になっているのか、それとも「経路品質を犠牲にして探索を分割しているだけ」なのかを明確に評価してほしい。
