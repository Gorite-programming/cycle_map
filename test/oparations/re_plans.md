# CycleMap 自転車ナビ Google Maps 互換度 90% 達成計画

> 対象: `re_test/` 次期アプリ系統。作業者: 人間が割り当てたAIエージェント。
> この文書は現在の実行計画・受入条件の正本。旧採点値や過去の作業ログより、この文書と現在のコード・実測結果を優先する。
> 関連: `re_test/overhaul_plan.md`、`re_test/plans.md`、`re_test/parity_checklist.md`、`re_test/prompts/integration_fix.md`、ルート `AGENTS.md`。

## 1. 目的と範囲

CycleMap の次期系統 `re_test/` を、Google Maps の**自転車ナビ主要導線**に対して証跡付きで90%以上の互換度にする。対象導線は「地図を見る → 施設を探す → 行き先を選ぶ → ルートを比較する → ナビする → 走行を記録する」。Google Maps の全機能を再現する計画ではない。

対象は `re_test/` のAndroidアプリ、アプリが必要とする県別オフラインデータ生成・導入手順、テスト・実機検証・評価資料。`application/` はパリティと切替条件が満たされるまで本番として維持する。`test/` は参照用とし、重大な不具合対応以外の機能開発先にしない。置換・削除・正式配布は本計画の達成だけでは実行せず、人間の承認を別途必要とする。

Google Maps のタイル、Places、Directions、画像、ロゴ、アイコン、商標、スクリーンショットを製品へ流用しない。Google Maps の画面資料は比較評価に限って扱い、CycleMap の成果物・テスト資産・配布物へ取り込まない。自転車向け経路比較では、標高、坂、階段、道路種別も比較材料にする。[Google Maps公式の自転車ルート情報](https://blog.google/products-and-platforms/products/maps/three-new-maps-updates-to-help-plan-your-next-adventure/)

## 2. 不変条件

1. **完全オフラインを基準にする。** 地図、検索、経路探索、案内、走行記録の主要機能は機内モードで成立させる。オンライン機能は任意の補助とし、無効・未接続・失敗・タイムアウト時はローカル動作を維持する。
2. **データの用途を混ぜない。** ルーティング用OSM `.graph` と地図描画用PMTiles/ラスターを分離する。OSM・地理院等の帰属表示をオフライン時も維持する。
3. **現行本番を保護する。** `application/` は全パリティ項目の実証、採点合格、人間の切替承認が済むまで破壊的変更をしない。
4. **破壊的操作をしない。** 大容量データ、`work/`、`venv/`、`local.properties`、keystore、既存のユーザー未追跡ファイルを移動・削除・上書きしない。端末データの消去、アプリデータ初期化、機内モード等の端末設定変更は明示的な許可なしに行わない。
5. **Git反映をしない。** `git add` / `commit` / `push` を行わず、差分・テスト・実機結果を報告する。
6. **タスク単位で停止する。** 受入条件またはテストが失敗したら、依存する後続タスクへ進まない。原因、再現手順、試した修正を作業ログに記録する。
7. **既知バグを先に読む。** `application/bugs.md`、`test/re_bugs.md` がある場合は該当領域を確認し、修正済み問題を盲目的に再実装しない。

## 3. 採点方法と90%の定義

### 3.1 評価対象

既存 `re_test/plans.md` の F1〜F9 / B1〜B9 と重みを初期基準として使う。Google Maps全般の機能数ではなく、CycleMap の自転車ナビ主要導線に関係する同一項目を比較する。重みはフロント合計82、バック合計90とする。

- フロント% = `Σ(項目重み × 項目得点) / 82 × 100`
- バック% = `Σ(項目重み × 項目得点) / 90 × 100`
- 全体% = `(フロント% + バック%) / 2`
- 合格条件は **フロント92%以上、バック88%以上、全体90%以上**。

### 3.2 0 / 0.5 / 1 の採点規則

- **0点**: 未実装、アプリ本体から未接続、主導線で利用不能、または必須オフライン機能が壊れている。
- **0.5点**: 一部実装・接続済みだが、受入条件、UI操作、実機確認、もしくは証跡のいずれかが不足している。
- **1点**: 項目の受入条件をすべて満たし、該当ユニット/UIテストと実機確認の証跡がある。
- 実機未確認の項目は最大0.5点。テストクラスやComposableが存在するだけでは加点しない。
- 「本体から接続済み」は、ユーザー操作からその機能が呼び出され、表示・状態・結果に反映されることを指す。文字列検索上の参照件数だけでは接続とみなさない。
- 各得点に、根拠となるテスト名、実機条件、証跡ファイル、未達理由を記載する。

### 3.3 旧スコアと数値の扱い

`FINAL_REPORT.md` / `scorecard_90percent.md` の90.15%を現在の確定値として引き継がない。計画開始時に現在のコード・操作・証跡を監査して再採点し、旧評価との差を記録する。テスト合計数は実行ログから集計し、NIGHT_LOGの時点別件数と最新値を混同しない。

## 4. 実施フェーズ

フェーズは番号順に実行する。各フェーズ内の項目は独立した小タスクに分け、各小タスクの受入後に次へ進む。

### Phase 0 — 現状監査と基準線

**作業**

- `re_test/` のコード、Gradle設定、テスト、`check_wiring.sh`、パリティ台帳、作業ログ、実機スクリーンショットを照合する。
- 対象機能を「定義のみ」「アプリから呼出済み」「画面操作で確認済み」「実機証跡あり」に分ける。
- 500行超ファイル、未接続クラス、失敗/保留テスト、未達パリティ項目を列挙する。
- Galaxy S21の接続可否と配置データを確認する。既存の端末データ・設定は変更しない。
- 現状スコアを本書 §3 に従って再計算し、各値を証跡へ結び付ける。

**受入条件**

- 実装・配線・テスト・実機証跡の状態が一つの監査表にまとまっている。
- 再利用可能な証跡と不適合証跡が区別され、未検証項目は未検証と表示されている。
- 以後の全タスクで使う、実行コマンド・端末・OS・データ版・基準コミットが記録されている。

### Phase 1 — オフライン地図と地図操作

**作業**

- ローカルPMTilesの読み込みURI、MapLibreのプロトコル登録、県別ファイル選択をコードから追い、機内モードの実機で描画を確認する。
- フォントglyphとspriteの参照先を調べる。外部URLを使わずに日本語ラベル・地図アイコンを表示できるファイル配置、配布、ライセンス手順を確立する。
- 広島県データで低・中・高ズームを選び、道路階層、水域、緑地、建物、鉄道、道路名、POI、現在地を確認する。
- ライト/ダークの地図とUIを同期する。タイル欠損は背景色で表現し、空白・黒・誤った県のタイルを出さない。
- 現在地の県を優先する選択、未導入県の表示、POIタップと地図カメラ移動、ルート線、帰属表示を確認する。
- 参考ズームは `z5/z10/z14/z17`。各表示でオンライン/オフライン差も記録する。

**受入条件**

- 機内モードでタイル、地名ラベル、アイコン、現在地、POI、ルート線、帰属表示が確認できる。
- 未導入県では未導入状態が明示され、他県のPMTilesに誤ってフォールバックしない。
- 4ズーム × ライト/ダーク × オフラインのスクリーンショットを保存し、確認対象をログに書く。
- 外部通信が発生しないことをログまたはネットワーク制御の検証で確認する。

### Phase 2 — 検索、POI、詳細情報

**作業**

- 検索入力から結果表示までに、正規化、ジャンル辞書、ランキング、DB検索が実際に使われるよう接続する。
- かな/カナ/ローマ字、全半角、濁点・長音、駅名、住所、カテゴリ検索、現在地からの距離順位を検証する。
- 連続入力では前の検索ジョブをキャンセルし、最新クエリの結果だけを表示する。DB処理はIOスレッドに置き、カーソルを閉じる。
- FTS5が使えないSQLiteでは `places.search_text` のLIKE検索へフォールバックする。`search_text` や営業時間等の列がない既存DBでもクラッシュさせない。
- POI詳細で名称、カテゴリ、住所、距離、お気に入り、電話/URL（存在時）、営業時間（判定可能時）を表示する。
- 営業時間は端末時刻とタイムゾーンを使う。`24/7`、休業、日またぎ、祝日、未知・不正値をテストし、判定不能なら営業状態を表示しない。

**受入条件**

- 実DBまたは固定テストDBを使って、検索 → 結果選択 → 詳細 → お気に入り操作が完結する。
- オフライン時に検索結果が得られる。旧DB・FTS5非対応時のフォールバックをテストする。
- 代表30クエリ以上で計測し、Galaxy S21のウォーム検索レイテンシ p95 が120ms未満。クエリセット、反復回数、p50/p95を記録する。
- 検索・詳細画面のUI操作テストと実機スクリーンショットがある。

### Phase 3 — 自転車ルート選択と品質

**作業**

- 出発地/目的地入力から経路探索を呼び、移動モード、代替経路生成、時間推定を実UIに接続する。最優先は自転車モードとする。
- 最大3候補を距離、推定所要時間、標高差、道路種別、利用可能な坂/階段情報で比較する。情報のない項目は「不明」または非表示にし、作り上げない。
- 地図では選択経路を強調色、代替経路を薄色で表示し、候補カードと地図上の選択状態を同期する。
- 自転車禁止道路、高速道路、通行方向、一方通行、段差/階段タグの取り扱いを仕様に照らして検証する。OSMに情報がない場合の限界も記録する。
- 固定テストグラフ上のゴールデン経路を用意し、同一入力に対する距離・ノード列・コストの再現性を確認する。
- 実測GPXと同一の出発/到着点を評価セット化し、推定時間の誤差を測る。

**受入条件**

- 目的地選択 → 最大3候補の比較 → 候補切替 → 地図描画が一貫して動作する。
- 固定ケースで違法方向・通行不可道路を選ばず、ゴールデンテストが安定する。
- Galaxy S21上の広島市内代表ルート30回以上で探索p95が300ms未満。中央値/p95、経路長、ノード数を記録する。
- 実測時間との差が±15%以内を目標とする。達成できない場合、採点は満点にせず、ルート種別・勾配・停止時間等の誤差要因と対策を残す。
- ルート比較UIの操作テストと実機証跡がある。

### Phase 4 — ナビ、リルート、音声、走行記録

**作業**

- 実ルート進捗に基づき、次の操作、残距離、ETA、残時間、必要な車線ヒント、ミュート、到着状態を更新する。
- 案内距離トリガとターン分類を固定テストする。同じ案内を繰り返し音声再生せず、TTS利用不能時は視覚案内を保つ。
- 逸脱時は連続サンプルで判定し、探索中も旧経路を保持する。探索完了時に位置を再確認し、古い位置からの結果を無条件適用しない。
- GPX前景サービス、Activity再生成後の記録継続、停止、インポート/エクスポート、履歴表示を確認する。
- 画面常時点灯・高頻度GPS・カメラ追従がナビ終了や画面離脱後に解除されることを確認する。

**受入条件**

- 固定GPX逸脱ケースで成功率98%以上、各再探索が3秒以内。テストセットと成功/失敗数を記録する。
- ルート進捗に沿って案内表示・音声・地図上ルートが更新されるUI/実機証跡がある。
- アプリ再生成後に記録が二重化・消失せず、停止後にGPS/画面常時点灯が解除される。
- 記録データの日時/タイムゾーンとGPXパースの回帰テストがある。

### Phase 5 — UI品質、テーマ、アクセシビリティ

**作業**

- 検索、場所詳細、ルート選択、ナビのコンポーネントを実際のアプリ導線に組み込み、画面状態を一方向に管理する。
- 3段階シート、ドラッグ、閉じる操作、地図ジェスチャーとの競合、最小48dpタッチ領域、タップ伝播を検証する。
- オンライン/オフライン表示は固定領域の小さな状態表示に留め、切替によるレイアウト移動を1dp以内にする。
- 日夜テーマを地図とUIで同期する。文字列リソース、英語ロケール、contentDescription、フォント倍率1.3、幅360dpを確認する。
- 位置・方位・ナビ進捗の高頻度更新が画面全体を不要に再コンポーズしないことを測定する。

**受入条件**

- Compose UIテストが主要画面を実際に操作する。StateFlow値の比較だけのテストで代用しない。
- オンライン切替の前後で主要ボタンとシートの座標差が1dp以内。
- ライト/ダーク、360dp、フォント1.3、英語表示のスクリーンショット/UIテストがある。
- Galaxy S21でナビ中のカメラ追従とシート操作が破綻せず、測定結果を保存する。

### Phase 6 — 県別データの生成・管理

**作業**

- 必要な場合に限り、PMTiles生成を県別データパック生成・導入手順へ追加する。既存の検索DB/グラフ/インデックス/manifest/LICENSEの運用と整合させる。
- パッケージ内容とmanifestの必須項目を確定し、各ファイルの名前、サイズ、SHA-256、生成元データ/ツール版を記録する。従来の5点ZIP仕様を6点へ変える場合は、該当ドキュメント、検証、スクリプトを同じ変更単位で更新する。
- Androidのデータ管理画面で導入済み県、容量、検証状態、削除対象を表示する。更新は一時ファイル検証後にアトミック置換し、失敗時は旧データを保持する。
- OSM、地理院、PMTiles、フォント、sprite等の出典・ライセンスをパック内とアプリ内に記載する。

**受入条件**

- 対象県をクリーンな一時出力先へ再生成し、manifest検証と全ファイルハッシュが一致する。
- 端末導入後に機内モードでPhase 1〜4の必要データを読める。
- 破損/中断した更新で既存の有効データが消えないテストがある。
- 生成・配置・検証手順が別エージェントに再現可能な記述になっている。

### Phase 7 — 総合QA、再採点、切替準備

**作業**

- JVMテスト、Compose UIテスト、ビルド、配線チェック、静的スタイル/レイヤーテストを実行する。
- Galaxy S21で機内モードとWi-Fiの各状態を使い、地図、検索、ルート比較、ナビ、記録、データ不足、ライト/ダークを検証する。
- 証跡は当該機能を実際に表示するものだけを使う。古い・不適合な証跡は削除せず、不適合と明記して置き換える。
- 受入条件に基づいて再採点し、全項目の証跡パス、実機可否、未達理由、テスト件数をまとめる。

**最終受入条件**

- 全自動テストと `:app:assembleDebug` が成功し、コマンド、実行環境、件数、結果が記録されている。
- `check_wiring.sh` で各採点対象の接続状況と500行超ファイルが確認済み。未接続を満点扱いしない。
- フロント92%以上、バック88%以上、全体90%以上を証跡付きで満たす。
- パリティ台帳に未確認/未達が残る場合、90%達成とは別に切替不可と明記する。アプリ本番切替は人間の判断へ委ねる。

## 6. 性能測定条件

- 端末: Samsung Galaxy S21。OS版、ビルド種別、データパック版、温度/電源状態を記録する。
- 経路: 広島市内の固定出発/到着点、少なくとも30回。探索レイテンシp95 <300ms。
- 検索: 固定クエリ30件以上、ウォームアップ後に各クエリを複数回実行。p95 <120ms。

- リルート: 固定逸脱GPXを各ケース複数回、成功率98%以上かつp95 <3秒。
- レポートに個々の測定値または再計算可能なログを残す。平均値だけで合格にしない。

## 7. 作業単位と報告様式

1. 作業前に `git status --short --branch` を確認し、既存差分・未追跡ファイルを変更対象から除外する。
2. 1タスクは一つの受入可能な機能に限定し、機能配線・UI・データ生成を一括で変更しない。
3. 各タスクの終了時に関連ユニットテスト、アプリテスト、ビルド、`check_wiring.sh` の必要範囲を実行する。テストを省略した場合は理由を書く。
4. 作業ログには開始/終了、対象、変更ファイル、テストコマンドと件数、実機条件、証跡、スコア変更理由、未解決事項を記録する。
5. テスト失敗、端末未接続、データ不足は成功扱いせず、未確認として残す。Google Mapsの画像やデータを成果物へコピーしない。
6. Git反映は行わず、変更要約・差分・検証結果を報告して停止する。

## 8. エージェントの初回タスク

1. Phase 0のみを実施する。アプリ機能を追加・修正しない。
2. 監査表と再採点の根拠を作成し、Phase 1以降の作業順・依存関係・未解決ブロッカーを整理する。
3. 実機設定変更や未追跡ファイルの整理が必要な場合は実行せず、報告に判断事項として記載する。
4. Phase 0の受入条件を満たした報告を提出し、人間の次の指示を待つ。

## 9. 他資料との整合ルール

- 実行順・受入条件・採点の正本は本書とする。
- `re_test/plans.md` は既存要件・重み・技術仕様を参照する資料とし、本書と矛盾する過去の完了主張やスコアは現況として扱わない。
- `re_test/prompts/integration_fix.md` は過去監査と作業制約の資料。本書のフェーズ/受入条件を優先し、過去の開始フェーズ指定を現在の進捗とみなさない。
- `re_test/parity_checklist.md` は項目ごとに証跡を更新する。実機確認なしに✅へ変更しない。
- 県別ZIP構成、PMTiles、ライセンス表示に変更が及ぶ場合は `AGENTS.md`、`application/DISTRIBUTION_NOTES.md`、データ生成スクリプト、README類の影響を調査する。人間承認が必須と書かれたファイルは勝手に変更せず、提案として報告する。
